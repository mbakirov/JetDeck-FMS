# Навигационная база (NavDB, эпик E02)

Ядро получает навигационные данные из файла SQLite. Файл делает конвертер из FAA CIFP (ARINC 424-18, только США). Новый цикл AIRAC выходит каждые 28 дней.

```
FAACIFP18 ──navdb-cli convert──► navdb-<cycle>.sqlite ──verify, bench──► manifest.json ──► сервер (позже)
                                                                                              │
приложение: NavDBUpdater ──► NavDBStore (база из комплекта | загруженная) ──► NavDatabaseReader ──► SimEngine
```

## Цели пакета

| Цель | Где работает | Назначение |
|---|---|---|
| `ARINC424` | сборка | Разбор записей CIFP фиксированной ширины (132 колонки) |
| `NavDBBuilder` | сборка | Фильтр аэродромов, запись SQLite, отчёт, проверка `verify`, замер `bench`, фрагмент для тестов |
| `navdb-cli` | сборка, CI | Команды `convert`, `verify`, `bench`, `manifest`, `extract-sample` |
| `NavDB` | приложение | Схема и модуль чтения `NavDatabaseReader`. Только чтение |
| `NavDBUpdate` | приложение | Манифест, загрузка, проверка, замена файла, выбор базы, уведомления |
| `Kernel/NavData` | ядро | Протокол `NavDatabase` и типы данных. Модули FMS и Displays видят только их |

Конвертер написан на Swift, а не на Rust. Крейт `arinc424` (v0.4.1) читает только аэродромы, ВПП, точки и воздушные зоны. Радиосредств, ILS, трасс, процедур и заголовка с циклом в нём нет.

## Связь с ядром

- `SimEngine(initial:navData:)` получает базу при создании и передаёт её модулям FMS и Displays. База не меняется, пока существует ядро. Новая база применяется в новом `SimEngine`, то есть при перезапуске сценария.
- Запись полёта хранит `navData` (цикл, версия схемы, версия конвертера, SHA-256 исходного CIFP). `Replayer` отклоняет запись, если база другая. Версия контракта поднята до 2.
- Номер и даты цикла для страницы A/C STATUS: `navData.cycle` (`ident`, `effective`, `lastDay`).

## Схема SQLite (версия 1)

`PRAGMA user_version` и `meta.schema_version` равны `NavDBSchema.version`. Модуль чтения отклоняет файл другой версии.

| Таблица | Содержимое |
|---|---|
| `meta` | Версии схемы и конвертера, цикл, даты, имя и SHA-256 исходного файла. Времени сборки нет |
| `fix` | Все точки: аэродромы, пороги ВПП, курсовые маяки, VOR/DME/NDB, точки. Вид, идентификатор, регион ICAO, аэродром, координаты, строка исходного файла |
| `fix_rtree` | Пространственный индекс R*Tree для карты ND |
| `airport`, `runway`, `ils`, `navaid`, `waypoint` | Данные каждого вида точек, ключ `fix_id` |
| `airway_fix` | Точки трасс по порядку, ограничения высоты и направления |
| `procedure` | SID, STAR, заходы. Тип захода (тип маршрута ARINC 424) и ВПП |
| `procedure_transition` | Маршруты процедуры: переходы, общий участок, конечный этап захода |
| `procedure_leg` | Участки: path terminator, точка, рекомендованное средство, theta, rho, радиус дуги, курс, расстояние или время, ограничения высоты и скорости, вертикальный угол, центр дуги |

Ссылки участков на точки конвертер переводит в `fix_id`. Идентификатор, регион и код раздела ARINC 424 тоже записаны. Ссылка без точки в базе попадает в отчёт.

Один вход всегда даёт одинаковый файл: id идут по порядку строк исходного файла, времени сборки в файле нет. Тест `sameInputGivesTheSameFile` это проверяет.

## Фильтр аэродромов

Аэродром попадает в базу, если выполнены оба условия:

- покрытие самой длинной ВПП твёрдое (код `H` в записи аэродрома; в записи ВПП ARINC 424-18 поля покрытия нет);
- есть ILS с глиссадой (категория 1, 2 или 3) на ВПП длиной не меньше 5000 ft. LOC без глиссады, LDA, SDF и IGS не считаются.

У аэродрома в базе сохраняются все ВПП, все ILS и LOC, все процедуры и все точки аэродрома. Маршрутные точки, радиосредства и трассы сохраняются все. Точка другого аэродрома, на которую ссылается процедура, тоже записывается.

Цикл 2611: 13 319 аэродромов до фильтра, 713 после. Отклонены: мягкое покрытие 8 314, нет ILS 4 273, ВПП с ILS короче 5000 ft 19 (список в отчёте конвертера).

## Отчёт конвертера

`make navdb-convert` пишет `build/reports/navdb-convert-<cycle>.json`:

- число прочитанных записей каждого типа, записей с ошибкой и записей продолжения;
- число записей, пропущенных по плану (воздушные зоны `UC`, `UR`, MSA `PS`, точки пути `PP`, вертолётные площадки `H*`, сетка MORA `AS`);
- аэродромы до и после фильтра, причины отказа;
- ссылки без точки в базе, повторы номеров участков;
- статистика path terminator по всем процедурам (для выбора типов участков в E07) и типов заходов;
- размер и SHA-256 базы.

Цикл 2611: 397 309 строк, 0 ошибок, 3 ссылки без точки (ошибки в данных FAA: центр дуги `KDPA` с кодом EA, VOR `DSM`, средство `SN` без кода раздела). Размер базы 22 МБ (6,8 МБ в gzip).

## Проверки

`make navdb-verify` сравнивает базу с исходным файлом. Исходный файл читает отдельный код по колонкам, не парсер конвертера, а базу — `NavDatabaseReader`.

- Для каждого аэродрома в базе: каждый маршрут каждой процедуры (SID, STAR, все заходы, в том числе ILS) есть в базе с тем же числом участков.
- Выборка 20 аэродромов разного размера (от 2 до 90 процедур): координаты порогов и длины ВПП, частота, курс, ВПП и координаты курсового маяка ILS.

Цикл 2611: 7 783 процедуры, 1 169 заходов ILS, 120 732 участка, расхождений нет.

## Время запроса для ND

`make navdb-bench` выполняет `fixes(near:radiusNM: 320, kinds: [])` 50 раз в 10 точках (KJFK, KORD, KATL, KDEN, KLAX, KSEA, PANC, PHNL, TJSJ, PASY у меридиана 180°).

| | Результат (Mac, Apple Silicon, release) |
|---|---|
| Больше всего точек | KORD, 9 429 |
| p50 по всем точкам | 2,1 мс |
| p99 по всем точкам | 5,5 мс |
| Максимум | 6,6 мс |

Порог: p99 не больше 20 мс (`NAVDB_P99_MS`). Это длина одного шага ядра. Запас относительно замера на Mac — около 3,5 раза, для iPad его нужно проверить замером в E12. Карта ND запрашивает данные только при смене масштаба или положения и хранит рисунок по номеру версии (E08), поэтому запрос не выполняется в каждом шаге.

Индекс: R*Tree. Обычный индекс по `(lat, lon)` дал близкое время при выборке всех колонок (около 10 мс против 9 мс в sqlite3), но он читает всю полосу широт по всей ширине США. R*Tree ограничивает и широту, и долготу.

## Обновление в приложении

1. `NavDBUpdater.update()` читает манифест по адресу `manifestURL`. Адрес пока не выбран, это параметр.
2. Если версия схемы в манифесте другая, загрузки нет: нужен новый выпуск приложения.
3. Если база в манифесте не новее активной, загрузки нет. Новее: следующий цикл, либо тот же цикл с новой версией конвертера или другим исходным файлом (исправление).
4. Файл загружается во временный файл в каталоге базы.
5. `NavDBStore.install` проверяет размер и SHA-256, открывает файл модулем чтения (версия схемы, `meta`), выполняет `quick_check` и сравнивает идентичность файла с манифестом.
6. Файл заменяет прежний атомарно (`replaceItemAt`). При любой ошибке временный файл удаляется, прежняя база остаётся.

`NavDBStore.openActive()` выбирает базу при запуске сценария: загруженную, если она открывается и её цикл не старше базы из комплекта, иначе базу из комплекта. Без сети работает база из комплекта.

### Манифест

```json
{"format": 1, "schemaVersion": 1, "builderVersion": 1, "cycle": "2611",
 "effective": "2026-10-29", "lastDay": "2026-11-25",
 "url": "navdb-2611.sqlite", "sizeBytes": 21970944,
 "sha256": "…", "sourceSHA256": "…", "notices": []}
```

`url` может быть относительным (относительно адреса манифеста) или абсолютным. `make navdb-manifest` пишет `build/navdb/manifest.json`.

## Цикл CI

`make navdb-cycle` выполняет `navdb-fetch`, `navdb-convert`, `navdb-verify`, `navdb-bench`, `navdb-manifest`. `AIRAC=next make navdb-cycle` готовит следующий цикл: FAA публикует архив заранее. `make check` сеть не использует.

Черновик задачи: `.github/workflows/navdb-cycle.yml`. Задача запускается по расписанию и вручную и сохраняет базу, манифест и отчёты как артефакт. Публикации нет: место хранения ещё не выбрано.

## Уведомления об ошибках в данных CIFP

Условие FAA: получатель CIFP сообщает своим пользователям об ошибках в данных.

**Ответственный:** владелец продукта JetDeck FMS. Он может назначить другого человека, тогда эту строку нужно изменить.

**Источники сведений об ошибках**

- сообщения пользователей;
- сведения FAA: файлы `CIFP Readme` и `Not_In_CIFP` в архиве каждого цикла, уведомления и NOTAM на процедуры;
- отчёт конвертера: ссылки без точки в базе, ошибки разбора;
- результат `navdb-verify`.

**Порядок**

1. Ответственный проверяет сведение в течение 2 рабочих дней.
2. Если ошибка подтверждена, он добавляет запись в `Docs/navdb-notices.json` (формат `NavDataNotice`: `id`, `kind`, `cycle`, `issued`, `title`, `message`, `airports`).
3. `make navdb-manifest` включает записи в манифест. Приложение показывает их после следующей проверки обновлений.
4. После подключения APNs (E12) то же уведомление уходит push-сообщением: ключ `navdb` в полезной нагрузке, формат тот же (`NavDataPush`).
5. Об ошибке в исходных данных ответственный сообщает в FAA. Контакт указан в заголовке файла CIFP (`HDR05`: «REPORT DATA ERRORS TO FAA»).
6. Исправление выходит в следующем цикле или как исправленная база того же цикла.

## Тестовый фрагмент

`SimCore/Tests/Fixtures/CIFP-sample-2611.txt` — часть CIFP 2611, 2 678 строк. Аэродромы: KJFK, KMRY, KACK, TJSJ, PANC, KBTV проходят фильтр; KCRQ (ILS на ВПП короче 5000 ft), KASE (нет ILS), 13FD (мягкое покрытие, ВПП без курса), 5KE (гидроаэродром) не проходят. Фрагмент сохраняет исходные концы строк CR LF (`.gitattributes`). Новый фрагмент: `make navdb-sample`.

## Критерии приёмки

| Критерий | Проверка |
|---|---|
| Конвертер обрабатывает полный файл без ошибок | `make navdb-convert`: 0 ошибок (цикл 2611) |
| Отчёт: число записей каждого типа и пропущенных | `navdb-convert-<cycle>.json`: `records`, `skippedByDesign`; тест `reportOfTheSample` |
| Фильтр по критериям, число аэродромов до и после | `airportFilter` в отчёте; тесты `filterRules`, `reportOfTheSample` |
| Все заходы ILS, STAR и SID с полным списком участков | `make navdb-verify` по всей базе; тест `verifierPassesOnTheSample` |
| 20 аэродромов: координаты ВПП, частота и курс ILS | `make navdb-verify`, раздел `sample`; тест `verifierFindsAChangedDatabase` |
| Объекты ND в радиусе 320 NM быстрее порога | `make navdb-bench`: p99 5,5 мс при пороге 20 мс |
| Без сети работает база из комплекта | тест `bundledDatabaseWorksWithoutNetwork` |
| Новая база загружается без нового выпуска | тест `newDatabaseIsInstalledAndUsed` |
| Неверная контрольная сумма отклоняется, остаётся прежняя база | тест `fileWithWrongChecksumIsRejected` |
| Номер и даты цикла для MCDU | `NavDatabase.cycle`; тест `identityAndCycleForTheMCDU` |
| Процесс уведомления об ошибках и ответственный | раздел выше |
